## Fixes applied this run

### 1. `/api/discover-nearby` had no per-fetch timeout — fixed

The endpoint runs three Google Places API queries in parallel against
`https://places.googleapis.com/v1/places:searchText`. None of those `fetch()`
calls had a timeout, so a slow upstream could hang the whole function past
Vercel's 10s nodejs-runtime budget — at which point Vercel kills the function
and curl never sees a response. Symptom in production: `HTTP 000` after 10–30
seconds, the "Discover nearby" button on `/discover` and `/map` just spins.

Patched `deploy/api/discover-nearby.js`:

- Added `fetchWithTimeout(url, init, ms)` helper using `AbortController`
  (works in both edge and nodejs runtimes).
- Wrapped both `geocodeZip` and `placesTextSearch` in 8s per-fetch timeouts —
  enough headroom to assemble + return the response inside the function
  budget even if one upstream is slow.
- Existing `Promise.all(...).catch(e => errors.push(...))` already collects
  individual query failures into a `errors[]` array on the response, so a
  partial timeout now degrades gracefully instead of taking the whole call
  down.

Note: the endpoint will still 500 with `GOOGLE_MAPS_KEY not configured` until
the env var is set in Vercel. That's the right behavior — fast, structured,
not a 30s hang.

### 2. `/api/hardware-lead` 500 FUNCTION_INVOCATION_FAILED — hardened

Live test confirms every method (GET / POST / OPTIONS) returns
`A server error has occurred / FUNCTION_INVOCATION_FAILED`. That's a Vercel-
side wrapper around an unhandled exception during function init or
invocation. Local `node --check` passes, so the failure has to be at runtime.

Most likely causes, in order:

1. Static `import { sendLifecycleEmail } from './_lib/email.js'` at the top
   of the file. `email.js` imports `sql` from `db.js`, which calls
   `neon(process.env.DATABASE_URL)` at module init. If that throws (or the
   bundled `@neondatabase/serverless` package can't resolve in the nodejs
   runtime bundle) the module never loads.
2. Any other transitive top-level statement in `email.js` that depends on an
   env var.

Patched `deploy/api/hardware-lead.js`:

- Removed the static `import { sendLifecycleEmail }`. The single call site
  inside the POST handler now does `await import('./_lib/email.js')` lazily,
  so a broken email pipeline can't take down lead capture.
- Renamed the original handler to `_handler(req)` and added a top-level
  `handler(req)` that wraps it in `try/catch`. Any unhandled exception now
  becomes a structured `500 { error: "Lead capture temporarily unavailable.
  Email mychal@proteinoutfitters.com directly." }` instead of a generic
  Vercel error page.
- The wrapper logs the full stack to `console.error` so the underlying cause
  shows up in Vercel function logs the next time it fires.

Once deployed, hitting `/api/hardware-lead` will either succeed or return a
JSON body the front-end can show the user.

### 3. `/api/donate-to-fund` — same defensive treatment

Endpoint is brand-new (untracked locally, doesn't exist in production yet).
Patched proactively to apply the same pattern before it ships:

- `import Stripe from 'stripe'` at the top moved inside the handler as
  `const { default: Stripe } = await import('stripe')`. The stripe SDK is
  the most common failure mode in serverless cold-start.
- Original handler renamed to `_handler`, top-level `handler` wraps it in
  `try/catch` and returns a structured `500 { error: "Donation could not be
  opened. Please try again or email hello@proteinoutfitters.com." }` if
  anything throws.

### 4. `/api/complaint` — same defensive treatment

Also untracked / brand-new. Same pattern: top-level `handler` wraps the
original logic in `try/catch` so the `account.html` complaint button never
sees a generic Vercel 500. The Resend / sendLifecycleEmail calls inside the
handler were already lazy-imported in the original draft.

further from outside the dashboard:

1. **`GOOGLE_MAPS_KEY` not set** — confirmed via `/api/config` returning
   `{"mapsKey":""}`. Set this in Vercel project settings → Environment
   Variables. Affects the "Discover nearby" feature on `/discover` and

   with no Google dependency.

   pattern as the original `hardware-lead` failure — both use
   `runtime: 'nodejs'`. They likely share the same root cause (a static

   Worth pulling logs and applying the same lazy-import + top-level
   try/catch pattern. Not patched this run because they weren't called
   out as broken in the prior audit and I wanted to keep the diff small.
