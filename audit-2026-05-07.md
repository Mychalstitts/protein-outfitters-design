## Fixes applied this run

### 1. Missing `/api/complaint` handler — created

`account.html` calls `POST /api/complaint` when a buyer files a quality complaint
about a reservation. The endpoint didn't exist, so the entire complaint flow was
silently broken in production.

Created `deploy/api/complaint.js` with:
- `POST` — validates `reservation_id` + ≥10-char message, ties the row to the
  existing reservation, copies `buyer_email/name` into the `complaints` table for
  ops triage even if the reservation is later deleted.
- `GET` (admin) — lists 200 most recent, optional `?status=` filter.
- `PATCH` (admin) — updates `status`, `resolution`, `refund_cents`.
- Best-effort acknowledgment email to the buyer (`Complaint.received` template)
  and ops alert to `OPS_COMPLAINTS_EMAIL` / `HARDWARE_LEADS_EMAIL` /
  `mychal@proteinoutfitters.com`. Both are wrapped in try/catch so the
  complaint is never lost if the email pipeline blips.

Schema already exists in `api/migrate.js` — no migration needed.

### 2. Missing `/api/donate-to-fund` handler — created

`donation-flow.html`'s primary donate button calls `POST /api/donate-to-fund`,
expects `{url}` back to redirect to Stripe. The endpoint didn't exist — every
donation button hit "Could not open donation: unknown" in production.

Created `deploy/api/donate-to-fund.js` with:
- Validates `STRIPE_SECRET_KEY`, $5–$50,000 amount range, optional donor email.
- Inserts a `pledged` row in `donation_funds` so `stripe-webhook` can flip it
  to `received` once the charge succeeds.
- Creates a Stripe Checkout Session with `submit_type: 'donate'`,
  `statement_descriptor_suffix: 'PO FUND'`, success / cancel URLs back to
  `/donation-flow`. Carries `kind: 'donation_fund'` and `fund_id` in metadata
  so the webhook can resolve the row.

### 3. Missing `/api/donation-funds` handler — created

`donation-flow.html` reads `GET /api/donation-funds?summary=public` to render
the live "$X in the fund · Y contributors · Z kill fees paid" stats below the
donate button. Endpoint didn't exist — the placeholder `$28k` stayed even after
real money came in.

Created `deploy/api/donation-funds.js` with:
- `GET ?summary=public` — public, no auth, 60s edge cache, returns
  `{ balance, funded_amount_total, contributors_count, fees_paid_total, fees_paid_count }`.
  Computed from `donation_funds` (received) minus `donation_disbursements` (sent).
- Graceful fallback: if the schema isn't migrated yet, returns a zeroed payload
  with a `note` instead of 500-ing — so the page still renders on a fresh DB.
- `GET` (admin) — full ledger.
- `POST` (admin) — manual entry (grants, sponsorships, etc.).

### 4. `/farm/:slug` rewrite blocked by literal directory — unblocked

`vercel.json` declares `{ "source": "/farm/:slug", "destination": "/farm-profile.html" }`,
but `producers.html` links to 12 farm slugs and only 2 (`northfield-pastures`,
`twin-pines-ranch`) returned 200 in production. The other 10 hit 404.

Root cause: a literal `deploy/farm/` directory contained two hand-crafted HTML
files. Vercel's static-file lookup happens before rewrites, and when a directory
exists at the rewrite source path, non-matching slugs 404 instead of falling
through to the rewrite. (Confirmed by direct test against ~6 unique slugs; the
identical `/produced → /producers` redirect in the same `vercel.json` does work,
which rules out a config-not-deployed theory.)

Fix: moved both literal files to `deploy/farm-archive/` (preserves the
hand-crafted designs as static archives) and emptied `deploy/farm/`. After the
next deploy:
- Every `/farm/<slug>` URL renders via the dynamic `farm-profile.html` template,
  which fetches `GET /api/farms?slug=<slug>` and renders whatever the DB knows.
- Slugs not in the DB get a graceful "Farm not found" 200 page instead of a
  hard 404.
- The two hand-crafted designs are preserved in `farm-archive/` should we want
  to revive them as bespoke landing pages later.

Tradeoff: `/farm/northfield-pastures` and `/farm/twin-pines-ranch` lose their
unique designs and inherit the generic template. Both farms are in the DB
(verified live: `GET /api/farms?slug=northfield-pastures` returns the real
record), so functionally everything still works.

### 5. Three `/brand/po-favicon.svg` 404s — fixed to `/brand/favicon.svg`

`discover.html`, `farm-profile.html`, and `farm/twin-pines-ranch.html` (now in
`farm-archive/`) referenced a favicon path that doesn't exist (`/brand/po-favicon.svg`).
Browser tabs on those pages showed the default globe icon instead of the brand
mark, and `/brand/po-favicon.svg` returned 404 on every page load.

Fixed all three to `/brand/favicon.svg`, which exists at the correct path.

## Open items not fixable from this audit

These need either (a) Vercel env vars or (b) production log access:

1. **`/api/discover-nearby` times out** — handler requires `GOOGLE_MAPS_KEY`.
   `GET /api/config` returns `{"mapsKey":"","geminiAvailable":true}`,
   confirming the env var isn't set. Either set the key in Vercel or short-
   circuit the handler with a clearer 503. Affects map "discover nearby"
   feature on `/discover` and `/map`.
2. **`/api/hardware-lead` returns 500 `FUNCTION_INVOCATION_FAILED`** on every
   method (GET, POST, OPTIONS). Local Node syntax check passes — this looks
   like a runtime crash on import (probably the `Resend` package or
   `sendLifecycleEmail` blowing up at module-load time when an env var is
   missing). Pull the function logs from Vercel to diagnose; the
   `/hardware` quote form silently fails until this is fixed.
3. **`GOOGLE_MAPS_KEY` env var** — without it, the Snapchat-style `/map` page
   renders the dark base layer but skips the Google-only insights drawer
   (already gracefully degraded — not a bug, but worth setting before launch).
4. **Cron jobs** — `vercel.json` registers `/api/email-tick` (daily) and
   `/api/annual-donor-acknowledgment` (Jan 15 yearly). Both exist as files; I
   couldn't trigger them from outside without the cron-secret. Worth a manual
   curl with `Authorization: Bearer $CRON_SECRET` from the dashboard to
   verify.
